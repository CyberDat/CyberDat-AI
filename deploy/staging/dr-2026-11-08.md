# CyberDat application Disaster Recovery — 2026-11-08

## Scope and evidence

Result: **PASS for the tested WordPress application recovery scope**, with the
limitations below. This is not a complete production VPS recovery certificate,
staging deployment, CyberDat prototype-theme acceptance or permission to deploy.

Evidence is the owner's Windows PowerShell/Docker/GPG/Python command output and
explicit confirmation on 2026-11-08. The audit agent was connected to the VPS and
did not directly control Windows Docker. This dated report is not a live status
probe. No password, private key, SQL, credential-bearing configuration or raw
archive contents is included.

The backup set is `20261108T082620Z-g8muao`, created on 2026-11-08 and copied
encrypted from the VPS to Windows 11. Its format and future recovery procedure
are documented in [backup.md](backup.md): three GPG archives plus `manifest.json`,
`SHA256SUMS` and `COMPLETE`. The private decryption key remained on Windows.

## Method

1. Verify a separately recorded hash of `SHA256SUMS`, all listed encrypted artifacts
   and manifest, and the completion marker. Verify local GPG decryption and complete
   gzip/tar integrity without printing contents or persisting a plaintext SQL dump.
2. Restore SQL through binary-safe streams into independent MariaDB 11.8.6,
   `cyberdat-restore-db`, using `cyberdat-restore-db-data`. Network mode was `none`,
   with no published ports and database events disabled. Check all 18 tables.
3. Keep that source instance separate. Create new working DB and WordPress volumes,
   stream a logical DB copy into working MariaDB and check all 18 tables again.
4. Validate archive paths/types, reject unsafe links/collisions, exclude production
   `wp-config.php` and runtime configuration, and copy 4866 WordPress files into the
   new working volume. Compare file hashes against the verified archive; normalize
   ownership to 33:33, directories 0755 and files 0644. Two entries were excluded.
5. Use new local database credentials/salts and a protective MU layer. Disable
   mail, WordPress outbound HTTP, HTTP Cron and updates before bootstrap. Verify
   PHP 8.4.27/Apache 2.4.69 and configuration syntax. Add and check `pdo_mysql` in
   the pinned-base local image; all requested extensions then loaded.
6. Verify the official WP-CLI GPG signature and use WP-CLI 2.12.0. Run URL dry-runs
   with a temporary READ ONLY database guard. Apply six replacements from the
   production HTTPS origin to `http://127.0.0.1:8088` in the working DB only,
   preserving serialized values and excluding GUIDs. Set stored `blog_public=0`;
   confirm actual options with direct SQL because a local `pre_option` safety filter
   had masked the stored value from `wp option update`. Final dry-runs for HTTPS,
   HTTP and www variants reported zero remaining replacements in checked fields.
7. Use an internal-only WordPress/MariaDB network. Docker Desktop did not activate
   a port binding for the internal-only web container. A separate Nginx 1.30.6
   reverse proxy, with internal and entry bridge connections, published only
   `127.0.0.1:8088`. It had no DB secrets or WordPress mounts, ran as UID 101 with
   read-only root and temporary paths in tmpfs. Verify actual runtime publication.
8. Set a distinct local administrator password with hidden input and stdin; no
   plaintext password file, command argument or report output. Verify login and
   invalidate local administrator sessions. Test guest and administrator HTTP
   paths without creating materials. Production credentials were not used for login.

## Limitations and remaining acceptance

- Editor and content creation were not tested; no test materials were created.
- Uploads was empty: media restoration and image-processing recovery were not
  exercised. Configuration symlink targets were not fully restored/tested.
- Production Nginx/PHP-FPM, TLS/ACME, OS services, permissions and scheduled jobs
  were not recovered on an independent VPS. Local Apache plus proxy is different.
- Full Windows-host/network isolation was not proved. Tested external TCP
  connections failed in isolated diagnostics; no successful connections were seen
  on selected host ports. This is not an all-protocol/all-port isolation proof.
  The entry proxy has potential egress; WordPress/MariaDB remain internal-only.
- SQL and file/config archives are not a single atomic snapshot. Concurrent DDL
  or filesystem changes require separately reviewed consistency measures.
- RTO/RPO were not measured; no recovery-time or recovery-point SLA is claimed.
- The CyberDat theme, offline CISA/NVD snapshots, frontend/editor workflows and
  future agent integrations require their own staging checks. False live flags
  and HTTP/mail hooks are not a hostile-code sandbox or general SMTP egress proof.
- GUIDs were intentionally excluded from URL replacement; zero dry-run matches
  does not prove absence of all production references or integration credentials.
